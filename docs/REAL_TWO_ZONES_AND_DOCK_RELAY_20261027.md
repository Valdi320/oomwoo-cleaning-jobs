## 2. Exact Nav2 goal UUID controls ROS2 docking velocity handoff

The new nav_lease_witness module requires the exact ROS2 goal UUID
that was fsync-journaled before Nav2 dispatch to be observed ACTIVE
during the CURRENT velocity lease and then terminal with a matching
persisted result. An old latched terminal status from another run
cannot authorize docking. An unknown active Nav2 goal immediately
revokes the lease.

The new ros_dock_velocity_relay is an EXPERIMENTAL LAB-ONLY ROS2 node.
It listens to separate Nav2 and OOMWOO dock_drive Twist inputs, ROS2
GoalStatusArray, odometry, battery and dock-drive status; it emits to
only ONE output: /valdi/lab_safe_cmd_vel_output.

The output is deliberately NOT the robot motor topic /cmd_vel.
The node refuses to start without simulation_lab enabled. The exact
UUID journal path must be configured for Nav2 source authorization.

Real ROS2 middleware/ROSIDL test with SYNTHETIC action/status, odometry
and battery input, but NO motor connections, confirmed:
- NAV input passes only after observing the exact current active UUID.
- DOCK input passes after exact terminal UUID and quiet odometry.
- A previous run's terminal UUID cannot authorize another run.
- Unknown active Nav2 goals revoke NAV ownership.
- Later Nav2 actions revoke DOCK ownership.
- Low battery and stale owner commands force output zero.
- Conflicting service request IDs are rejected.
- Relay finishes STOPPED and reports motor_hardware_connected=false.

Machine evidence:
[evidence/ros2_exact_uuid_dock_relay_20261027.json](evidence/ros2_exact_uuid_dock_relay_20261027.json).

Run only in a private offline DDS domain with the experimental
ros2_lab_interfaces ROSIDL package built and sourced:

    PYTHONPATH=src python3 integration/ros_dock_velocity_relay_probe.py

Actual OOMWOO Nav2/dock-drive cmd_vel remapping and MCU motor ingress
MUST be reviewed before hardware. None were deployed here.

## 3. Existing OOMWOO geometric docking

The UNMODIFIED upstream oomwoo_dock.dock_harness ran in OOMWOO's
official Jazzy image: **7/7 docking scenarios succeeded in its own
2D kinematic/LiDAR simulator**, at ±25.5 mm lateral bay margin.

This is independent, ALREADY EXISTING OOMWOO work, NOT a feature
written by this contribution and not Gazebo or physical proof.
The default upstream dock_drive publishes its own cmd_vel; running
that along with Nav2 without a verified exclusive mux would be unsafe.

## 4. Remaining blockers to production/physical 100%

- Official test_room has no independently verified electrical charge
  current, dust-empty or mop-wash provider/telemetry protocol.
  Docked=true is geometrical, not proof that services happened.
- Independent MCU cliff/bumper/watchdog, wheel-drop/current limits,
  physical stopping and motor command ownership are not validated.
  The experimental relay does NOT send commands to actual motors.
- A furnished, physically partitioned multi-room world with real
  doors and dynamic obstacles, SLAM shifts/restarts and long
  endurance has not passed a whole-home acceptance suite yet.
- Canonical cleaning-jobs ROS2 action/service API and exclusive Nav2
  ownership still need maintainer review and standard OOMWOO bringup
  integration; the contributor PR changes only its owned pointer.
- Real swept-area credit must be gated by actual vacuum/mop actuator
  telemetry and calibrated physical localization. Simulator ground
  truth is not proof that physical dirt was removed.

The two-zone DIGITAL scope is **100% externally measured in Gazebo**;
the complete physical robot and service station remain unverified.
